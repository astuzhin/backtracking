# Summary of `backtracking_numba.py`

Этот файл реализует трассировку релятивистского протона назад во времени в
магнитном поле IGRF. Код специально написан просто: основной публичный вход -
функция `trace_proton_backtracking(...)`, а вспомогательные функции нужны только
для нормы вектора, вычисления поля IGRF, правой части ОДУ и одного шага RK45.

## Что трассируется

Состояние частицы хранится как 6 чисел:

```text
y = [x, y, z, ux, uy, uz]
```

где:

```text
x, y, z     координаты в Earth-centered Cartesian, km
ux, uy, uz  единичный вектор направления движения
```

Выходной массив `trajectory` имеет 7 колонок:

```text
t_s, x_km, y_km, z_km, ux, uy, uz
```

Важно: `ux, uy, uz` - это не скорость в km/s, а единичное направление. Модуль
скорости считается отдельно из кинетической энергии и остается постоянным.

## Системы координат

Координаты в трассировщике - геоцентрические декартовы координаты в km:

```text
X: долгота 0 градусов, экватор
Y: долгота 90 градусов востока, экватор
Z: северный географический полюс
```

Для вычисления IGRF текущая декартова точка переводится в сферические
геоцентрические координаты:

```text
r     = sqrt(x^2 + y^2 + z^2)
rho   = sqrt(x^2 + y^2)
colat = acos(z / r)
elong = atan2(y, x)
```

`igrf14syn(...)` вызывается с `itype = 2`, то есть `alt` означает расстояние от
центра Земли в km, а не высоту над поверхностью:

```text
bn, be, bd = IGRF north, east, down components, nT
```

После этого локальные компоненты `north/east/down` переводятся обратно в
декартовы компоненты. Если

```text
sin_phi = y / rho
cos_phi = x / rho
sin_theta = rho / r
cos_theta = z / r
```

то базисные векторы:

```text
north = (-cos_theta*cos_phi, -cos_theta*sin_phi,  sin_theta)
east  = (-sin_phi,             cos_phi,           0)
down  = (-sin_theta*cos_phi, -sin_theta*sin_phi, -cos_theta)
```

и поле:

```text
B_cart_nT = bn*north + be*east + bd*down
B_cart_T  = B_cart_nT * 1e-9
```

Интегратор работает с полем в Tesla.

## Релятивистская скорость

На вход подается кинетическая энергия протона `kinetic_energy_gev` в GeV.

Используются константы:

```text
c = 299792.458 km/s
proton rest energy = 0.9382720813 GeV
proton mass = 1.67262192369e-27 kg
elementary charge = 1.602176634e-19 C
```

Релятивистский фактор:

```text
gamma = 1 + K / mp_c2
```

где `K` - кинетическая энергия в GeV, `mp_c2` - энергия покоя протона в GeV.

Далее:

```text
beta^2 = 1 - 1/gamma^2
v = c * sqrt(beta^2)
```

`v` хранится как `speed_km_s`, то есть в km/s.

## Уравнения движения

Интегрирование идет не напрямую по времени, а по длине пути `s` в km. Это
удобно, потому что модуль скорости постоянен, а направление меняется под
действием магнитного поля.

Физически сила Лоренца:

```text
dp/dt = q * (v_vec x B)
```

Для постоянного модуля скорости:

```text
v_vec = v * u
p = gamma * m * v * u
```

Отсюда:

```text
du/dt = q / (gamma*m) * (u x B)
```

Так как `ds/dt = v`, а в коде `s` измеряется в km:

```text
du/ds_km = q / (gamma*m*v_km_s) * (u x B)
```

В коде правая часть ОДУ:

```text
dr/ds = u
du/ds = curvature * (u x B)
```

где:

```text
curvature = charge_sign * e / (gamma * proton_mass_kg * speed_km_s)
```

`B` здесь в Tesla, `speed_km_s` в km/s, поэтому производная получается на km
пути.

## Знак заряда и backtracking

В функции есть строка:

```text
charge_sign = sign(charge) * -1
```

Это означает, что пользовательский `charge` превращается во внутренний
эффективный заряд с обратным знаком. Так реализована трассировка назад:
положительный протон на входе трассируется как частица с противоположным знаком
в прямом параметре интегрирования.

Практически:

```text
charge = +1  backtracking для протона
charge = -1  обратный знак для тестов обратимости
```

## RK45

Один шаг выполняется функцией `_rk45_step(...)`. Используется схема
Dormand-Prince RK45:

```text
k1 ... k7
```

На одном и том же наборе промежуточных правых частей строятся две оценки:

```text
y_next  решение 5-го порядка
y4      решение 4-го порядка
```

Разность `y_next - y4` используется как оценка локальной ошибки.

Нормированная ошибка считается отдельно для координат и направления:

```text
scale_position  = 1e-6  + 1e-8 * max(abs(y[i]), abs(y_next[i]))
scale_direction = 1e-10 + 1e-8 * max(abs(y[i]), abs(y_next[i]))
```

Итоговая ошибка шага:

```text
err = max(abs(y_next[i] - y4[i]) / scale_i)
```

Шаг принимается, если:

```text
err <= 1
```

После принятого шага направление снова нормируется, чтобы численная ошибка не
уводила `u` от единичной длины.

## Адаптация шага

Внутренний шаг всегда хранится как `ds` в km.

Есть два режима задания начального шага:

```text
step_mode = 0  начальный шаг задается как ds0_km
step_mode = 1  начальный шаг задается как dt0_s, затем ds = v * dt0_s
```

После первого шага адаптация все равно работает по `ds`.

Если шаг принят:

```text
factor = 0.9 * err^(-0.2)
```

Если шаг отвергнут:

```text
factor = 0.9 * err^(-0.25)
```

Фактор ограничен диапазоном:

```text
0.2 <= factor <= 5.0
```

Если `err == 0`, следующий шаг увеличивается в 5 раз.

## Время и длина пути

Хотя интегрирование идет по `s`, в выходной массив записывается время:

```text
t = t + ds / speed_km_s
```

То есть `t_s` - накопленное физическое время в секундах, соответствующее
пройденной длине пути при данной релятивистской скорости.

Сама длина пути `s` внутри функции накапливается, но в выходной массив не
записывается.

## Условия остановки

Параметр `stop_cond_mode` задает, когда остановить трассировку:

```text
0  только по радиусу: r < r_min_km или r > r_max_km
1  только по длине пути: s >= s_stop_km
2  только по времени: t >= t_stop_s
3  по радиусу или длине пути
4  по радиусу или времени
```

Для режимов с фиксированной длиной пути последний шаг обрезается так, чтобы не
перешагнуть `s_stop_km`. Аналогично для фиксированного времени шаг обрезается
через оставшееся время:

```text
remaining_s = (t_stop_s - t) * speed_km_s
```

Для радиальных границ специальной интерполяции до точной поверхности сейчас нет:
остановка происходит после шага, когда новая точка уже оказалась за границей.

## Статусы возврата

Функция возвращает:

```text
trajectory, n, status
```

где `n` - индекс последней реальной записанной точки. Реальная траектория:

```python
traj_real = trajectory[:n + 1]
```

Статусы:

```text
 1  пересечен r_max_km
 2  достигнут s_stop_km
 3  достигнут t_stop_s
 0  достигнут max_steps
-1  пересечен r_min_km
-2  некорректное начальное направление, заряд или энергия
-3  точка ушла ниже внутреннего радиуса применимости IGRF
-4  некорректные настройки stop_cond_mode / step_mode / границ
```

## Память и Numba

Массив траектории выделяется сразу:

```text
trajectory.shape = (max_steps + 1, 7)
```

Это удобно для `numba`, потому что размер массива известен заранее, а внутри
JIT-функции не нужно динамически расширять Python-список. Неиспользованная
часть массива после `n` не является реальной траекторией.

## Ограничения текущей версии

Текущая реализация:

```text
- использует только IGRF;
- не включает TS05 или другое внешнее магнитосферное поле;
- считает энергию и модуль скорости постоянными;
- использует фиксированную дату IGRF на всю трассировку;
- интегрирует в геоцентрической декартовой системе, не в GSM;
- не делает точную интерполяцию радиального пересечения r_min/r_max;
- хранит в выходе время, но не хранит накопленную длину пути s.
```

Для добавления TS05 наиболее естественный следующий шаг - интегрировать в GSM,
а IGRF на каждом шаге временно считать через обратный переход в GEO и затем
переводить поле обратно в GSM.
